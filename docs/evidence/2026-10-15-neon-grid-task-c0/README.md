However, there is no support-only instance mesh: the named industrial architecture batch combines foundations, roof plant units, facade ribs, and loading bays. Keep the housing/slat color distinction: the base-color texture will multiply the existing vertex colors (`#42505d` housing, `#9ba3b2` slats), so the A/B must review the resulting values and hues at racing distance. No per-instance material or extra draw group is needed for the selected target.

### Chase-camera visibility check

A source-pinned browser fixture used the Task A visual selector at Undercity progress 0.355, Medium quality, eight racers, chase view, 1280×720 CSS viewport at DPR 1.5 (actual drawing buffer 1920×1080). Headless Chromium with SwiftShader reported no page, console, or HTTP errors. From the 16 vent banks, 9 projected into the viewport; only 3 had any target-first hits in a 3×3 ray sample across their projected bounds. The other in-frame samples were blocked mainly by `undercity-wallside-sightline-screens`, with some hits on buildings or a racer. The three partially exposed banks had estimated geometry-box bounds of about 24×15, 51×33, and 22×14 CSS pixels (roughly 36×23, 77×49, and 32×21 drawing-buffer pixels at this DPR). Those boxes overestimate the visible textured area; this is not a pixel-level surface segmentation.

The scene uses linear fog with near 180 and far 650 units. These three bank centers were about 49–80 units from the camera, before the fog start, so fog did not explain their limited visibility in this fixture. The current chase view exposes only a few small, partly occluded vent surfaces. The target remains as selected; C1 should treat racing-distance readability as a primary A/B go/no-go question. These measurements cover one desktop chase state and do not establish visibility across all sectors, portrait view, rear view, or physical devices.

Evidence: [unmodified chase screenshot](undercity-chase-desktop-1920x1080.png), [machine-readable visibility report](vent-chase-visibility.json). The screenshot SHA-256 is recorded in the JSON. The report describes ray-sample occlusion, not pixel contribution or device performance.

The first affects foundations, roof units, ribs, and loading-bay doors together. The second adds a separate batch/draw and requires new accounting against the existing graphics budgets. The public publisher statements support the CC0 1.0 designation, but this packet is not a binary-ready provenance/hash record. Before C1 implementation, obtain the exact publisher package through an authorized accessible source and record its archive/map filenames, file formats, dimensions, SHA-256 values, conversion commands, final 1024×1024 dimensions, and final hashes. If access remains blocked, keep the binary and runtime work paused; do not substitute another texture.

For the selected painted-metal stack, use only base color, normal, and roughness initially. The source page lists the normal as DirectX; convert it to OpenGL orientation (or validate and document the equivalent material-space inversion). Omit AO and height. Add the metallic map only if the fixed A/B comparison shows a clear benefit. Base color is sRGB; normal, roughness, and metallic data are linear. Preserve the one instanced draw batch and existing vertex colors. The source package's optional packed workflows are not needed for this first proof.

Planning-only memory estimate: three 1024² RGBA8 maps require about 16 MiB with a full mip chain; four maps require about 21.3 MiB. This estimates decoded storage under those assumptions, not actual GPU residency. Compressed package size, actual browser/GPU storage, and texture memory deduplication remain unmeasured.
